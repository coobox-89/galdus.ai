# Deployment

This guide builds and runs Galdus.ai in production, step by step. Two setups are covered:

- **A. Zero-cost hosting** (current public preview): GitHub Pages (console) + Render (API, Docker) + Supabase (PostgreSQL).
- **B. One server with Docker Compose**: database, API, console and an HTTPS proxy on a machine you control.

The day-to-day runbook (deploy, rollback, secret rotation, backups, incidents) is in [OPERATIONS.md](OPERATIONS.md). Every variable is listed in the [reference](#environment-variables) at the end.

> [!IMPORTANT]
> Type secrets only into the provider dashboards (Render, Supabase, GitHub) or your server's `.env`. Never into chat, issues, commits or `VITE_*` variables: everything in a `VITE_*` variable is public.

Once signed in as a platform admin, **Platform admin, Setup** in the console shows which features are on and walks through each one (redirect URIs to copy, Render variables, check again).

## Build for production

| Part | Command | Output |
|:--|:--|:--|
| API image | `docker build -t galdus-api apps/api` | Python 3.12 image, unprivileged user, dependencies pinned by `apps/api/requirements.lock` |
| Console | `cd apps/web && npm ci && VITE_API_BASE_URL=https://<api-host>/api npm run build` | `apps/web/dist` (static files with a Content Security Policy that allows only that API) |
| Console for GitHub Pages | `npx vite build --base=/galdus.ai/` | Same, served under the repository path |
| Console image | `docker build --build-arg VITE_API_BASE_URL=/api -t galdus-web apps/web` | nginx serving the console and proxying `/api` |
| Desktop | `cd apps/web && npm run tauri build` | Installers per platform (see `apps/desktop/README.md`) |

CI (`.github/workflows/ci.yml`) runs on every pull request: API tests against PostgreSQL with pgvector, migration round-trip and drift check, OpenAPI drift check, `pip-audit` and `npm audit` (high and critical block), secret scan (gitleaks), the console build, both Docker images and the Playwright end-to-end suite.

## A. Zero-cost hosting: GitHub Pages, Render, Supabase

### A1. Database on Supabase

1. Create a project in an EU region (for example Frankfurt). Save the database password in a password manager.
2. **Database, Extensions**: enable `vector` (schema `extensions`).
3. **SQL Editor**, as `postgres`: create the application role, with a long random password generated on your computer:

   ```sql
   create role galdus_app with login password 'REPLACE_WITH_RANDOM_PASSWORD';
   grant usage, create on schema public to galdus_app;
   alter role galdus_app set search_path = "$user", public, extensions;
   ```

   `galdus_app` owns the tables its migrations create. It is not a superuser and not the Supabase `service_role`.
4. **Connect, Session pooler**: copy the host. Render has no IPv6, so use the session pooler (port `5432` on `*.pooler.supabase.com`), not `db.<ref>.supabase.co`. The URL for the API:

   ```
   postgresql+asyncpg://galdus_app.<PROJECT_REF>:<PASSWORD>@<POOLER_HOST>:5432/postgres?ssl=require
   ```

   Only with the transaction pooler (port `6543`) set `DB_TRANSACTION_POOLER=true`.
5. After the first deploy, open **Advisors, Security**: no table may be reported as exposed. Migrations enable row-level security on every table and revoke `anon` and `authenticated`; a test in CI fails if a new table misses it.

### A2. API on Render

1. Render, **New, Blueprint**, repository `coobox-89/galdus.ai`. Render reads `render.yaml` (service `galdus-api`, Docker, Frankfurt, free plan, health check `/readyz`).
2. In **Environment**, fill every `sync: false` variable. Required: `DATABASE_URL` (A1.4). `JWT_SECRET` and `ENCRYPTION_KEY` are generated by Render: copy `ENCRYPTION_KEY` into your password manager now (see [OPERATIONS.md](OPERATIONS.md#rotate-secrets)).
3. Optional features, each off while its variables are empty: sign-in providers and drives (A4), email (A5), scheduler (A6), `ADMIN_EMAILS` (your address; it becomes platform admin once confirmed).
4. Deploy. With `RUN_MIGRATIONS_ON_START=true` the container runs `alembic upgrade head` before serving (with a Postgres advisory lock, so two starts cannot both migrate). If migrations or the configuration check fail, the new version does not go live and the previous one keeps serving.
5. Check:

   ```bash
   curl -s https://galdus-api.onrender.com/health   # {"status":"ok","version":"..."}
   curl -s https://galdus-api.onrender.com/readyz   # {"status":"ready","database":"ok","migrations":"ok",...}
   ```

With `ENVIRONMENT=production` the API refuses to start when a required value is missing or still a development value: short or placeholder `JWT_SECRET`, missing `ENCRYPTION_KEY` (or equal to `JWT_SECRET`), wildcard or `http` CORS, default `DATABASE_URL`, non-https or localhost `PUBLIC_API_URL`/`FRONTEND_URL`, `SMTP_HOST` without `SMTP_FROM`, rate limits turned off. `/docs` is hidden; the API reference is [API.md](API.md).

### A3. Console on GitHub Pages

1. Repository **Settings, Pages, Source: GitHub Actions**.
2. **Settings, Secrets and variables, Actions, Variables**:
   - `GALDUS_API_BASE_URL` only if the API is not at `https://galdus-api.onrender.com/api`.
   - `LEGAL_EMAIL` (required before public sign-ups), optionally `LEGAL_ADDRESS`, `LEGAL_OPERATOR`, `LEGAL_COUNTRY`: shown in the privacy policy and terms.
3. **Actions, Deploy web to GitHub Pages, Run workflow** (it also runs on every push to `main` that touches `apps/web`).
4. Make sure `CORS_ORIGINS` on Render is `https://coobox-89.github.io` and `FRONTEND_URL` is `https://coobox-89.github.io/galdus.ai`.

GitHub Pages cannot send response headers, so the console carries its Content Security Policy as a `<meta>` tag and GitHub serves HSTS for `github.io`. Framing protection (`frame-ancestors`) needs a header: use setup B, or a custom domain behind a proxy, if that matters to you.

### A4. Sign-in with Google, GitHub, Microsoft and cloud drives

Redirect URIs use `PUBLIC_API_URL` (here `https://galdus-api.onrender.com`).

| Feature | Where to create the app | Redirect URIs | Render variables |
|:--|:--|:--|:--|
| Google sign-in and Google Drive | Google Cloud Console, APIs and services, Credentials, OAuth client ID (Web). Enable the Google Drive API. Consent screen: External, scopes `openid email profile drive.readonly`, then publish. | `.../api/v1/auth/oauth/google/callback` and `.../api/v1/connectors/google/callback` | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` |
| GitHub sign-in | GitHub, Settings, Developer settings, OAuth Apps, New OAuth App. Homepage: the console URL. | `.../api/v1/auth/oauth/github/callback` | `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` |
| Microsoft sign-in, SharePoint and OneDrive | Microsoft Entra, App registrations, New registration, "any organizational directory and personal accounts", platform Web. Delegated Graph permissions `openid`, `email`, `profile`, `User.Read`, `Files.Read.All`, `Sites.Read.All`, `offline_access`. Create a client secret. | `.../api/v1/auth/oauth/microsoft/callback` and `.../api/v1/connectors/microsoft/callback` | `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `MICROSOFT_TENANT` (`common`) |

Google and GitHub accounts are linked to an existing Galdus account only when the provider reports the email as verified. Microsoft can create new accounts (their address is then confirmed by email) but is never linked to an existing account by email.

### A5. Email (verification, password reset, invitations)

Any SMTP provider works (Brevo, Resend, Mailgun, Amazon SES; several have a free tier). Verify the sender domain with the provider (SPF and DKIM), then set `SMTP_HOST`, `SMTP_PORT` (`587` STARTTLS or `465` TLS), `SMTP_USER`, `SMTP_PASSWORD` and `SMTP_FROM` (for example `Galdus <no-reply@yourdomain>`). Then consider `REQUIRE_EMAIL_VERIFICATION=true`: password sign-in waits for the confirmation and registration stops revealing which addresses already have an account.

### A6. Scheduler

Generate a random value (`python3 -c "import secrets; print(secrets.token_urlsafe(48))"`), set it as `AUTOMATION_TOKEN` on Render and as the repository secret `GALDUS_AUTOMATION_TOKEN`. `.github/workflows/automation-tick.yml` then runs every 15 minutes: scheduled automations, the daily drive re-sync and data retention (records older than 24 months, expired links).

### A7. Free plan limits and how to live with them

| Limit | Effect | What to do |
|:--|:--|:--|
| Render free instance sleeps after about 15 minutes idle | The first request after a pause takes 30 to 60 seconds | The scheduler and uptime workflows wake it every 15 to 30 minutes. For real traffic use a paid instance (always on). |
| Render free: 750 instance hours a month, no pre-deploy step, one instance | Enough for one always-awake service; migrations run at container start | Keep one instance. On a paid plan set `RUN_MIGRATIONS_ON_START=false` and uncomment `preDeployCommand` in `render.yaml`. |
| Render free: in-memory rate-limit counters reset on restart | Lockout windows restart after a deploy | Set `RATE_LIMIT_BACKEND=postgres` to keep counters in the database (one small write per limited request). |
| Supabase free: 500 MB database, paused after 7 days without activity | Large knowledge bases fill the quota; a paused project makes `/readyz` fail | The scheduler keeps it active. Watch **Reports, Database size**; delete unused collections; upgrade before 400 MB. |
| Supabase free: no downloadable daily backups or point-in-time recovery | You own the backups | Run `scripts/backup-db.sh` weekly ([OPERATIONS.md](OPERATIONS.md#backups)). |
| GitHub Actions schedules can run late by several minutes | Automations run at most every 15 minutes, sometimes later | Expected; for exact timing use a paid cron (for example Render Cron) calling the same endpoint. |

## B. One server with Docker Compose

Requirements: a Linux server with Docker and Compose, a domain whose DNS points at it, ports 80 and 443 open.

```bash
git clone https://github.com/coobox-89/galdus.ai.git && cd galdus.ai
cp .env.example .env
# Edit .env: DOMAIN, POSTGRES_PASSWORD, JWT_SECRET, ENCRYPTION_KEY (all random and different),
# ADMIN_EMAILS, SMTP_* and the optional providers. Leave ENVIRONMENT=development here:
# the production overlay sets ENVIRONMENT=production and the public URLs for the API.
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.prod.yml ps
curl -s https://$DOMAIN/readyz
```

The overlay adds Caddy (automatic Let's Encrypt certificates, HSTS) in front of the console container, which proxies `/api` to the API; the database, API and console are not published on the host. The `migrate` service applies migrations before the API starts. Upgrades: `git pull` and the same `up -d --build` command.

For self-hosted models (Ollama, vLLM, LM Studio) on the same machine or network set `ALLOW_PRIVATE_MODEL_ENDPOINTS=true` and use `http://host.docker.internal:11434` as the base URL.

## Smoke test before inviting people

1. `/health` and `/readyz` answer, `/readyz` shows `"migrations":"ok"`.
2. Register, finish or skip the tour, confirm the email (if SMTP is set), sign out and in.
3. Connect a model with the wizard and chat: the answer streams.
4. Upload a document, search it, ask about it in a chat grounded on the collection.
5. Create an agent and run it; create an automation and use **Run now**.
6. Invite a second account; check it sees the workspace with its role, and that it gets 403 on a workspace it does not belong to.
7. Try a wrong password six times: the account is locked for 15 minutes (HTTP 429).
8. Turn on two-step verification, sign in with it, download your data, delete a test account.
9. Open the console on a phone.
10. Read the Render logs: JSON lines with routes and status codes only, no prompts, tokens or keys.

## Environment variables

API variables (`apps/api/app/config.py`). Required means the API refuses to start in production without a valid value.

| Name | Purpose | Required in production | Example (not real) |
|:--|:--|:--|:--|
| `ENVIRONMENT` | `production` turns on the startup checks, HSTS and hides `/docs` | Yes | `production` |
| `DATABASE_URL` | PostgreSQL connection for the API and migrations (asyncpg driver) | Yes | `postgresql+asyncpg://galdus_app.<ref>:<password>@<pooler-host>:5432/postgres?ssl=require` |
| `JWT_SECRET` | Signs access tokens; at least 32 random characters | Yes | `<48 random characters>` |
| `ENCRYPTION_KEY` | Encrypts provider keys, drive tokens, MCP headers, TOTP secrets, OAuth state; at least 32 characters, different from `JWT_SECRET`. Back it up | Yes | `<48 random characters>` |
| `CORS_ORIGINS` | Comma-separated console origins allowed to call the API (https, no wildcard) | Yes | `https://coobox-89.github.io` |
| `PUBLIC_API_URL` | Public API address, used for OAuth redirect URIs | Yes (https) | `https://galdus-api.onrender.com` |
| `FRONTEND_URL` | Public console address, used in emails and redirects | Yes (https) | `https://coobox-89.github.io/galdus.ai` |
| `RUN_MIGRATIONS_ON_START` | `true`: the container runs `alembic upgrade head` before serving | No (Render free: `true`) | `true` |
| `FORWARDED_ALLOW_IPS` | Proxies whose `X-Forwarded-For` uvicorn trusts | No | `*` behind Render or Caddy |
| `CLIENT_IP_HEADER` | Header with the real client IP set by your edge (overrides the above for rate limits) | No | `cf-connecting-ip` |
| `ADMIN_EMAILS` | Comma-separated platform admins (granted once the address is confirmed) | No | `owner@example.com` |
| `REQUIRE_EMAIL_VERIFICATION` | Sign-in waits for email confirmation; registration does not reveal existing accounts | No (recommended with SMTP) | `true` |
| `JWT_EXPIRE_MINUTES` | Session length | No | `30` |
| `LITELLM_MODEL`, `ALLOWED_MODELS` | Optional platform model and allowlist (workspaces normally bring their own keys) | `LITELLM_MODEL` must be in `ALLOWED_MODELS` | `openai/gpt-4o-mini` |

| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Google sign-in and Drive | No | `<from Google Cloud>` |

| `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `MICROSOFT_TENANT` | Microsoft sign-in, SharePoint and OneDrive | No | `<from Entra>`, `common` |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` | Outgoing email | No (`SMTP_HOST` needs `SMTP_FROM`) | `smtp-relay.example.com`, `587`, `<user>`, `<password>`, `Galdus <no-reply@example.com>` |
