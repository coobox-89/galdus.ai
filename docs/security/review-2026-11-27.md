# Security review, 27 November 2026

Pre-production review of Galdus.ai at commit `2771226` (0.9.1), on branch `release/production-readiness`. Method: reading every API module, the console's authentication and integration code, the migrations and the workflows; running the test suites against PostgreSQL 16 with pgvector; scanning the git history and the dependencies; checking headers, CORS and logs on a running API; a browser audit of every page. Each fix has a regression test in `apps/api/tests/test_release_security.py` (named F1 to F13 below) or in the Playwright suite.

Outcome: **no open finding blocks the release**. Thirteen issues were fixed (two of them high severity). The residual risks at the end are accepted with the mitigations listed.

## Summary of checks

| # | Area | Checks run | Outcome |
|:--|:--|:--|:--|
| 1 | Authentication and sessions | JWT expiry, signature and audience (MFA tokens cannot be used as sessions), revocation on password change, reset and "sign out everywhere", logout everywhere, reset links (single use, 1 hour, hashed), MFA (TOTP replay, recovery codes single use and hashed), enumeration on login, registration and reset, lockout and rate limits on login, registration, reset and MFA | Fixed F1, F2, F3, F4; passes |
| 2 | OAuth | Encrypted state with expiry, provider and purpose checks, PKCE, browser-bound nonce cookie for sign-in, fixed redirect URIs built from `PUBLIC_API_URL`, no user-controlled redirect targets, account linking rules | Fixed F5, F6; passes |

## Findings and fixes

| ID | Severity | Finding | Fix |
|:--|:--|:--|:--|
| F4 | High | `ADMIN_EMAILS` granted the platform console at registration without proving the address. Anyone registering a listed address first (before the owner, or after the owner deleted the account) became platform admin with access to every user and workspace. | In production the flag is granted only once the address is proven: email link, password reset link, or Google/GitHub with a verified email. Outside production it still applies at registration for convenience. |
| F6 | High | Cloud-drive OAuth was completed by the callback alone. An admin could start a connection for their own workspace and send the provider's consent link to a victim; the victim's Google Drive or SharePoint tokens would then be stored in the attacker's workspace. | The callback only forwards `code` and `state` to the console; the signed-in session completes it with `POST /api/v1/connectors/{provider}/complete`, which requires the same user and workspace that started the flow. |
| F1 | Medium | Only per-IP limits on sign-in; with many IPs (or a spoofable forwarded address, see residual risks) passwords could be guessed without limit. | Per-account lockout: 5 failures in 15 minutes returns 429 until the window ends, for unknown addresses too (no enumeration). Works with the memory and Postgres backends. |
| F2 | Medium | Second-factor codes limited to 5 a minute per user, about 7,200 guesses a day. | At most 10 wrong codes per 15 minutes per account on verify, disable and recovery-code regeneration. |
| F3 | Medium | Registration answered 409 for taken addresses, which reveals who has an account. | With `REQUIRE_EMAIL_VERIFICATION` and SMTP, registration always answers 202 "check your inbox"; the owner of an existing account receives a private notice. Without SMTP the 409 remains (residual risk R2). |
| F5 | Medium | Microsoft sign-in was offered by the setup guide but not implemented, and Microsoft's email claim is not proof of ownership (a tenant can set any address). | Microsoft sign-in added with a strict rule: it can create a new, unverified account (confirmed by email) but is never linked to an existing account by email. A password reset drops sign-ins linked before the address was proven. |
| F7 | Medium | Inbound webhooks returned 500 on malformed bodies and had only a per-IP limit; each call runs a model. | 400 for invalid JSON, 422 for invalid input, and at most 10 calls a minute per automation. |
| F8 | Medium | Accounts created with Google or GitHub could not delete themselves (deletion required a password they never had). Deleting the only owner of a shared workspace left that team without an owner. | Password-less accounts confirm deletion by typing their email. Deletion is refused (409, with the workspace names) until another member is made owner. |
| F9 | Low | The data export held only profile, workspaces and usage. | Export format 2 adds conversations with messages, runs, linked sign-ins, preferences and security settings (never secrets). |
| F11 | Low | Logs included raw paths and query strings (webhook tokens in `/hooks/{token}`, OAuth `code` and `state`), and `httpx` logged full outbound URLs; SQL errors could include parameters; no CSP. | JSON logs with the route template, status, duration and request id only; uvicorn access log and noisy library loggers off; `hide_parameters` on the engine; uniform error bodies; CSP `default-src 'none'; frame-ancestors 'none'` on the API and a strict CSP on the console (scripts and connections only to itself and the API; no remote images, which also blocks image-based exfiltration from model output). |
| F12 | Low | Uploads were accepted by extension only. | PDF signature required; binary files renamed to text formats refused. |
| F13 | Low | Production start-up accepted an empty `ENCRYPTION_KEY` (MFA and OAuth then failed at runtime), placeholder secrets from `.env.example`, and http or localhost public URLs. | The production check now refuses all of these, plus `ENCRYPTION_KEY` equal to `JWT_SECRET`, `SMTP_HOST` without `SMTP_FROM` and disabled rate limits. |
| F10 | Info | RLS was on for every table, but nothing prevented a future migration from forgetting it. | A database test fails when any table in `public` lacks row-level security. |
| | Info | A password reset left other outstanding reset links valid; forgot-password emails were limited per IP only. | Using one link revokes the others; at most three reset emails per address per hour (the answer is unchanged). |

## Residual risks (accepted)

| ID | Risk | Why accepted | Mitigation |
|:--|:--|:--|:--|
| R1 | Behind Render, uvicorn trusts `X-Forwarded-For` from any proxy (`FORWARDED_ALLOW_IPS=*`) and takes the left-most address, which a client can forge, so per-IP limits can be bypassed. | Render does not document a fixed proxy address range. | Per-account lockout (F1, F2) and per-user limits do not depend on the IP. If your edge sets a trusted header, set `CLIENT_IP_HEADER`. |
| R2 | Without SMTP, registration reveals whether an address has an account (409). | Without email the API cannot tell the real owner. | Per-IP registration limit; configure SMTP and `REQUIRE_EMAIL_VERIFICATION=true` (owner checklist). |
| R3 | Access tokens (30 minutes) live in `sessionStorage`, readable by script on the console origin; the OAuth callback passes the token in the URL fragment (removed from history at once). | An httpOnly cookie session needs the API and console on the same site (not the case with github.io and onrender.com). | Strict CSP (no inline or third-party scripts), React escaping, short expiry, revocation; no secrets in the token. |
| R4 | DNS rebinding could defeat the private-address check between validation and connection for user-supplied URLs (web import, `web_fetch`, model base URLs, MCP). | Needs a pinned-resolver HTTP client in several libraries (LiteLLM, MCP). | Only owners and admins configure model and MCP endpoints; https required; responses capped; the API host has no sensitive internal services on Render. |
| R5 | A person who knows an address can lock that account for 15 minutes by failing its password repeatedly. | Standard trade-off of account lockout. | Short window; the owner can still reset the password; lockout events are visible in logs (429 on `/api/v1/auth/login`). |
| R6 | On GitHub Pages the console cannot send `frame-ancestors` or other headers (CSP is a meta tag). | Static hosting limitation. | Clickjacking needs the victim to act inside a framed console; sensitive actions ask for a password or a code. The Docker setup sends the headers. |
| R7 | Prompt injection through documents, web pages and tool results can still influence answers. | Inherent to LLMs. | Untrusted content fenced and known patterns neutralized; MCP tools allowlisted per server; delivery only to https webhooks; built-in tools are read-only and MCP tools that change data must be allowed one by one by an owner or admin. |
| R8 | The free Supabase plan has no provider-side downloadable backups. | Zero-cost hosting. | Encrypted weekly backups with `scripts/backup-db.sh`, quarterly restore drill ([OPERATIONS.md](../OPERATIONS.md#backups)). |

## How to reproduce

```bash
# API tests (PostgreSQL with pgvector required for the database tests)
cd apps/api && pip install -c requirements.lock -e ".[test]"
export DATABASE_URL=postgresql+asyncpg://galdus:<pw>@localhost:5432/galdus_test TEST_DATABASE_URL=$DATABASE_URL JWT_SECRET=<32+ chars>
alembic upgrade head && pytest -q
pip-audit -r requirements.lock --strict
# Console
cd ../web && npm ci && npm audit --audit-level=high && npm run build && npx playwright test
# Secrets
gitleaks git . --redact --config .gitleaks.toml
```

Results on 27 November 2026: 141 API tests passed, 18 end-to-end tests passed (Chromium; pages checked at 360, 768 and 1440 px), 0 vulnerabilities from `pip-audit` and `npm audit`, gitleaks clean with the fixture allowlist.
